# Operations runbook

Design and rationale live in [README.md](README.md). This file is the day-to-day
reference: what runs where, what needs a restart, how to check the pool is healthy,
and how the pieces are distributed.

## Components

**Two trees, not one.** The package is this repo (`~/Projects/lacode`). The
author's live opencode config is beside it at `~/.config/opencode`:
`opencode.jsonc`, `AGENTS.md`, `commands/`, `rules/`, `.opencode/prompts/`,
`.env`. Those are **not in git** and are not published — they are one person's
configuration. Paths below say which tree they are in: `bin/oc-sync` reads each item
from the tree that owns it, and a path resolved against the wrong tree ships the
wrong bytes.

| Path | Tree | Role |
|---|---|---|
| `presets/free-tier.json` | repo | the bundled default pool: models and weights. Resolution chain: plugin `models` option > `~/.config/lacode/pool.txt` (flat; `pool.json` also accepted) > this file. See `presets/README.md` |
| `src/agents.ts` | repo | the **18 agent keys the plugin injects** when the config lacks them: 5 bases (`build`, `plan`, `explore`, `implement`, `context`) plus 12 hidden `<base>-1..4` variants (3 pooled bases × 4 slots), plus the hidden `instructions` agent — the one writer of the project's root `AGENTS.md`, reachable only from `/agent-instructions`. Injection is merge-without-clobber, so a config that declares a name keeps its own. The variants declare **no model**: it is written from `presets/free-tier.json` |
| `src/commands.ts` | repo | the three `/context-init`, `/context-update`, `/context-review` commands, injected as inline templates the same way |
| `src/lib/pool.ts` | repo | shared state and the slot decision; imported by both plugins, exports no plugin |
| `src/lib/writer-rule.ts` | repo | startup check that the one-writer permission rule actually fires; imported by `context-autoupdate.ts` |
| `src/plugins/agent-pool.ts` | repo | task routing, limit detection, 30s hang reaper, `pool_status` |
| `src/plugins/context-autoupdate.ts` | repo | keeps `.opencode/context/` current; borrows a pool slot |
| `scripts/build.mjs` → `dist/` | repo | `npm run build` compiles `src/` to plain JS. `dist/` is gitignored and regenerated by `prepack`, so what ships is always a fresh build |
| `~/.config/opencode/opencode.jsonc` | **config** | the 8 agent keys the author's config still owns (3 built-in stubs + `build`, `plan`, `basic`, `expert`, `context`), the plugin entry, permissions, `instructions`. Everything else is injected |
| `.opencode/prompts/` | both | 7 prompt files, read by `build` and `plan` through `{file:...}`. Every injected agent's prompt is inline in `src/agents.ts`, not a file |
| `AGENTS.md`, `commands/`, `rules/` | **config** | the global instructions and the slash commands and rules they point at. Not in git; `oc-sync` ships them to the hosts |
| `bin/oc`, `bin/oc-sync` | repo | the `oc` launcher and the deploy script. Not published, and nothing in the package depends on them |
| `.env` / `.env.example` | config / repo | host list and deploy overrides. `.env` is gitignored and lives in the config dir; `.env.example` documents every variable |
| `~/.local/share/opencode/agent-pool/` | state | live cross-process claims + cooldowns |
| `~/.local/share/opencode/auth.json` | state | credentials — deliberately outside both trees |
| `.opencode/context/` | state | each project's context map — derived, not in git (see below) |
| `tests/` | repo | 19 suites, 132 tests, no network, no running server |

## Health checks

```bash
opencode run "pool_status"          # live load, cooldowns, watchdog liveness
tail -f ~/.local/share/opencode/log/opencode.log | grep -E "routed|cooling|hung|reaper"
```

`pool_status` is the authoritative check. Three things to look for:

- `watchdog alive: last sweep Ns ago (every 30s)` — if this exceeds ~60s the reaper
  is not running and hung tasks will hold their slot. It is the only positive signal;
  the reaper logs nothing when it finds nothing.
- `COOLING` on a slot — expected during rate limiting, and the pool routes around it.
- `hung … auto-aborted` — the reaper recovering a wedged task. Fine occasionally;
  repeatedly means a model or provider is unhealthy.

Log lines worth knowing: `routed <base> -> <variant>` on every pooled spawn,
`borrowed pool slot N … for auto update` when the cartographer runs,
`reaper armed` once per process at startup.

## Changing the pool models

Edit `presets/free-tier.json` (or drop a `pool.txt` — `model [weight]` per line, the flat form — or a `pool.json` in `~/.config/lacode/`, or pass `models` in the plugin tuple — the chain is documented in `presets/README.md`) — one entry per slot, array position is the slot number:

```json
{ "slots": [
  { "model": "opencode/big-pickle", "weight": 3 },
  { "model": "opencode-go/minimax-m3.1-flash-free", "weight": 2 },
  { "model": "opencode/deepseek-v4.1-flash-free", "weight": 1 },
  { "model": "opencode/glm-5.3-flash-free", "weight": 1 }
] }
```

At most **4 slots**: the plugin injects one hidden variant per base per slot from
`src/agents.ts`, so a fifth entry would route spawns at an agent that does not exist.
Entries past the fourth are dropped with a warning, not silently ignored.

`weight` is a slot's **share of the rotation** — how many turns it takes per cycle — and its
concurrency ceiling is **twice that**. Two rules, in order:

1. the weighted round-robin run (each slot one position per unit of weight, in list order:
   `3,2,1,1` → `1,1,1,2,2,3,4`) is walked from a shared cursor, and the first slot that is
   neither cooling nor at its ceiling takes the spawn, so no slot is drained before the others
   see work
2. once **every** slot is at its ceiling, the overflow goes to the least loaded slot, so a
   burst past the summed ceilings equalises instead of piling up or blocking

So `3,2,1,1` produces `1,1,1,2,2,3,4,…` — ordered preference, with the bottom of the list as
reserve. The ceiling is deliberately larger than the rotation share, so one full rotation fills
only half the pool and the run is walked twice before every slot is full; a burst that outruns
one rotation still lands on the heavy slot rather than falling straight through to overflow.
Equal weights give a plain round robin in list order.

Raise a weight to let a model take more turns — and hold twice as many concurrent sessions;
lower it to make it more of a reserve. No weight means `1`; anything that is not a number in
`(0, 100]` warns and means `1`.
`tier` is an accepted alias for `weight` — `primary` is weight 2, `overflow` is
weight 1 — read with a warning, so a host that has not picked up this file keeps two slots' worth
of headroom.

Do **not** add a `model` to a variant agent anywhere — they carry none on purpose. The
plugin's config hook writes `<base>-<slot>` for `explore`, `implement` and
`context` from this file, and appends a slot's model id to a provider whitelist that
already exists (it never writes one where you have none — an absent whitelist already allows
every model). A
`model` on a variant is a second source of truth that loses: the plugin logs `still hard-codes …
presets/free-tier.json wins` on every start. There is usually nothing to edit — the
variants are injected, not declared — so a hit here means the config defines one itself,
and that definition is the thing to delete.

Keep the provider configured in your own opencode config, and keep the models
tool-call capable — check with `curl -sS https://models.dev/api.json` or `opencode models
<provider>`. **Cost is never checked**: the loader validates shape only, and a paid or
proprietary model is as valid as a free one. The bundled preset is built from free models
because that is a good default, not because the pool requires it. What the pool *does*
need is the provider: it can append a model id to a provider's existing `whitelist`, but it cannot
invent a provider, so an unconfigured one leaves the slot resolving to nothing. Then
restart every opencode process and confirm what is actually live:

```bash
npm run build                   # this machine loads dist/, not src/
opencode debug agent explore-1   # model it resolved
opencode run "pool_status"            # slots, load/ceiling, cooldowns
```

Failure modes are logged, never silent: a bad entry (no `provider/model-id`, a repeated
model, a fifth slot) is dropped with a warning and the other slots still route; a bad
`weight` is only a preference, so it warns and keeps the slot at weight 1; a file that
yields nothing usable falls back to the built-in defaults. All of them appear in the log as
`presets/free-tier.json …`, so check
`tail -f ~/.local/share/opencode/log/opencode.log | grep free-tier` when a spawn
resolves to the wrong model or lands on an unexpected slot. If the plugin is disabled
(`opencode --pure`) the variants have no model at all and inherit the session's — check the
plugin is loading before debugging a wrong model.

## Restarts

**Plugins are not hot-reloaded.** Any change to `presets/free-tier.json`, the personal
`opencode.jsonc`, `src/lib/`, or `plugins/` requires restarting every opencode process.
Servers are foreground processes with no systemd unit or tmux session, so each is
restarted from its own terminal.

On **this machine** there is a step in front of that: the config loads
`dist/index.js`, so a change under `src/` needs `npm run build` before a restart means
anything. Editing `src/`, restarting, and concluding the change did not take is the
likely failure. The hosts have no build step — they load the `plugins/` shims — but they
do need a sync.

This bites in a specific way: a config change is invisible until restart, so a fix can
look applied and still not be running. Swapping a pool model is where it matters most:
the file says one thing, a long-running server keeps routing to the old one. Always check `ps -eo pid,lstart,comm | grep opencode`
against the file mtime before concluding a change is live.

## What opencode.jsonc holds now

The file is in the personal config dir, it is **224 lines**, and it is not
where the agents come from. `src/agents.ts` injects all 18 agent keys, variants
included, and they resolve (`opencode debug agent explore-1`).
Merge-without-clobber is why `build` and `plan` still appear in the config —
the config's own definitions win — which is what leaves 8 keys: the 3 built-in
stubs, plus `build`, `plan`, `basic`, `expert`, `context`.

- **None of the 12 pool variants are in it.** They are generated by the plugin,
  and a variant named in this file would be a definition the plugin cannot merge
  with its own.
- **Task rules use globs** (`explore*`), because opencode compiles a permission
  pattern to an anchored regex with `*` → `.*` and the longest match wins. Listing all
  four variants per base meant adding a line to two agents for every new slot.
- **The models are not there at all** — `presets/free-tier.json` owns them and the plugin
  injects them.
- **There is no Playwright grant, and adding one would do nothing.** opencode folds
  `agent.tools` into the permission list at config-load time, while decoding the
  config, so a `tools` value a plugin writes from its `config` hook is never read
  by anything. What the file carries is the top-level
  `"tools": { "playwright_*": false }`, which keeps the MCP tools away from every
  agent. **Browser automation is therefore off for the injected agents**, including
  the ones this file is run from. `src/agents.ts` carries the full reasoning under
  NOT INJECTED; read it before re-adding anything.
- `explore`, `general` and `implement` are disabled. These are opencode's built-in
  generic subagents; they would always be spawnable, cost a full-price model, and bypass
  `explore*` / `implement*` entirely. Only `basic`, `expert`, the pool bases and
  their variants, and the deep agents remain. `pool-test.mjs` pins this — against
  `tests/fixtures/opencode.json`, not this file — so a built-in that becomes usable
  fails there rather than quietly doubling the delegation paths.

> **Deploy.** Remote hosts are plain npm clients: install the plugin
> (`opencode plugin @lawaty/lacode -g`) and copy `opencode.jsonc`; there is
> nothing to rsync, and notifications use a direct ssh hop (`lacode tunnel setup`),
> not a systemd-held reverse forward. The `bin/oc-sync` flow below is the
> source-sync + reverse-tunnel path, and it still exists.

## Deploying to the other hosts

```bash
bin/oc-sync                    # every host in $OC_HOSTS, config included
bin/oc-sync --dry-run          # preview, writes nothing
bin/oc-sync --host <alias>     # one host
bin/oc-sync --scripts-only     # only `oc`, NOT the config
```

Pushes, with a remote backup first:

- **from the repo** — `oc`, `oc-notify`, `src/`, `presets/`, `plugins/`
- **from the personal config dir** — `opencode.jsonc`, `AGENTS.md`, `commands/`,
  `rules/`, `.opencode/prompts/`
- the tunnel key, from `~/.ssh/`

Each item is read from the tree that owns it: the script resolves every path
against one tree or the other, and a path resolved against the wrong tree ships
the wrong bytes. `.opencode/` is
pushed as `prompts/` only: it also carries a `package.json`, a lockfile and tens
of megabytes of `node_modules`, none of which belong on a host. `dist/` is **not**
pushed — the hosts load the plugin from the `plugins/` shims described below, not
from a build of this repo. `OC_SYNC_CONFIG_DIR` overrides the config dir; it is
what a second setup or a test points at.

**The config is the default, not an opt-in.** Plain `bin/oc-sync` ships the config
alongside `oc`; a run that ships only `oc` leaves a fix to `AGENTS.md` on this
machine while the hosts keep the rules they already have, and the run reports
success either way. Use `--scripts-only` when you genuinely want just the launcher.

**`AGENTS.md`, `commands/` and `rules/` are not optional extras.** `AGENTS.md` is the
global instruction file opencode auto-loads into every session, and `commands/` +
`rules/` are what it points at. A host missing them runs agents that were never told
`.opencode/context/` exists, and they will report skipping the map while claiming the
protocol was loaded. The failure is invisible locally in both directions: a host
carrying a stub `AGENTS.md` that claims the protocol arrived via `instructions` in
`opencode.jsonc` — a key nothing loads the map through — looks fine from here, and so
does a host with no `AGENTS.md` at all. If a host's agents ever deny reading
the map, diff the remote's `AGENTS.md` byte count against the local one before touching
anything else.

All three live in the personal config dir rather than in this repo, so they are read
from there and shipped from there — and they are **not under version control at
all**. They are the rules that generate every context map, so a change to one has
no history and no review; that is the one thing in this split worth deciding about
rather than living with.

A failed transfer is a failure, not a detail: every rsync's exit status is checked
before its output is filtered, and the host is listed under `failed` with the
directory left behind so you know what state it is in. `--dry-run` writes nothing at
all, locally or on the remote — it reports the `~/bin` PATH line, `OC_LOCAL_USER` and
`authorized_keys` entries it *would* add. `.opencode/context/` never crosses: only
`.opencode/prompts/` is transferred, and the map is the derived artifact of whatever
projects a host works on, so each host regenerates its own.

`oc-sync` passes `ClearAllForwardings=yes` to every ssh and rsync it makes. Each of its
~12 calls per host would otherwise compete for the tunnel ports and print `remote port
forwarding failed`; a half-claimed listener can also block the session that actually
needs the tunnel to notify you. The script itself never needs a forward — the
`oc-tunnel@<host>` units below hold those, and they are the only thing that should.

### Desktop notifications from a remote session

A notification raised on a host has to travel back to the desktop. The desktop is
behind NAT, so a direct ssh back times out and the return path must be a reverse
tunnel — and the tunnel's owner is whichever session connects first, so a session
that starts before the tunnel does has no notification path.

`oc-sync` installs one **systemd --user unit per host**, `oc-tunnel@<alias>`, holding
`ssh -N -T -R <port>:localhost:22 <alias>` with `Restart=always` and `enable-linger`.
Each host gets its own port, derived from its name. On the desktop side the
provisioning is a dedicated `~/.ssh/oc_notify` keypair (never your
personal key — this private half is on every host) whose `authorized_keys` entry
carries `restrict` plus `command=`, so a host can raise a notification and nothing
else.

```bash
systemctl --user status 'oc-tunnel@<alias>'   # is the tunnel up?
cat ~/.config/opencode/remote.env             # this host's desktop user + port
```

Four constraints, each with its failure mode if it is not met:

- **The tunnel must not belong to a login session.** A `RemoteForward` line in
  `~/.ssh/config` ties the listener to whichever ssh connection won the port race, so
  it exists only while that connection is alive and drops when the terminal closes.
  A session that finishes while no tunnel is listening notifies a port that does not
  exist, and nothing says so: the local end is a forced command, so there is simply
  nothing listening. The unit owns the lifetime. `oc-sync` removes any such
  `RemoteForward` lines (backed up to `~/.ssh/config.ocsync-backup`) so they cannot
  win the port race.
- **The desktop user must not come from the rc files.** `OC_LOCAL_USER` is exported
  from `.bashrc`/`.profile`, which covers an interactive ssh and nothing else. The
  notify plugin calls `oc-notify` as a *detached child of an already-running server*,
  where neither file is read; an unset variable falls back to `id -un` = `root`, and
  the hop dies with `root@localhost: Permission denied (publickey,password)`.
  `~/.config/opencode/remote.env` is readable by anything and rewritten on every sync.
  `oc` refuses to guess a username rather than produce a confusing publickey failure.
- **The dbus path must be the *local* uid.** A notify command built on the host, where
  `id -u` is `0` for root, produces `/run/user/0/bus` — which does not exist on the
  desktop. Every notification then vanishes silently.
- **One alias per machine in `.env`.** `dev-host` and `192.0.2.10` are the same host;
  listing both installs two units and flaps `remote.env` between ports on every sync.

Verify end to end, in the *worst* environment — a bare env is exactly how the plugin
calls it, so if this passes the plugin's path works:

```bash
ssh <alias> 'env -i HOME="$HOME" PATH=/usr/bin:/bin SSH_CLIENT="1.2.3.4 0 22"   setsid ~/bin/oc-notify "tunnel check" "post-sync smoke"'
```

No output means it landed. A failure now says which of the three things is missing.
See `tests/oc-test.mjs` for the checks that keep this wired.

### When a session needs you

`src/plugins/notify.ts` raises a notification when a session needs you, named after the
session, so a long task does not need a watched terminal. The policy lives in
`src/lib/notify.ts`, pure and testable without a running server.

How the module gets loaded differs by machine, and it is worth knowing which is
yours. **This machine** names it explicitly — the config carries
`"plugin": [["file:///…/Projects/lacode/dist/index.js", …]]`, so what runs is the
**build**, and `npm run build` is part of editing `src/`. **The hosts** get `src/`
and the `plugins/` shims and auto-discover those instead; no build step runs
there. A change to `src/` therefore does nothing on this machine until it is both
built and restarted, and on a host until it is synced and restarted.

```
opencode — Fix the login redirect     Task finished, waiting for your review
opencode — Deploy run                  Awaiting your response — Which option?
opencode — Deploy run                  Failed                        (critical)
```

Both are about what *you* must do, not about what opencode did. The wording is
"Task finished, waiting for your review" — accurate about both halves: the session
is still open, and the name on the notification is the session's.

What is deliberately **not** notified:

- **Session start.** It interrupts to say nothing — no result, no title, nothing to act
  on. A notification you learn to dismiss on sight is one you dismiss when it matters.
  `oc` sends none either.
- **Subagents.** `parentID` is set, so ten delegated `explore` children raise
  zero notifications. The value is one notice per thing you asked for.
- **The cartographer.** `context-autoupdate` spawns `context` through the
  session API with no `parentID`, so it is indistinguishable from a root session by
  structure alone; it is matched by title prefix instead. Without this, every file
  edit would announce the map update.
- **Compaction.** It idles the session but no task finished.
- **Sessions that never went busy.** Opening opencode is not completing work.
- **The idle that follows a question.** The task is parked, not finished, so it is one
  blocked moment reported once — and once you answer, the real completion notifies again.

A 5s cooldown per session per outcome absorbs queued-message and retry bursts. Two
outcomes exempt themselves: **errors**, and **questions** — both report a session that
is *blocked*, and gating those on a cooldown strands you on a prompt you were never
told about.

Delivery is a detached child of the server, so a notification can never hold it open.
The plugin resolves the helper (the `lacode` CLI, `dist/lacode.js`), calls it as
`lacode notify …` — the argv shape depends on which helper it found, so a `lacode`
helper gets the `notify` subcommand and an `oc-notify` helper does not — and logs
`notified` only when the helper exits zero with empty stderr. On a remote host the
hop is a direct ssh (`ControlMaster`), configured once with `lacode tunnel setup`.

A **permission** notification is the one that is not fire-and-forget. It carries
buttons — **Allow once**, **Always allow** and **Deny** — so the helper stays
attached and waits for the click; the chosen button's name comes back on its
stdout, and the plugin answers the permission with it through opencode's own API.
A permission already answered in the terminal is recognised rather than reported
as a failure, and a popup dismissed without a choice answers nothing. The wait is
bounded, and the buttons are Linux-only: `notify-send --action` is the only
channel that can offer one.

Restart opencode to load a plugin change; plugins are not hot-reloaded. A long-running
session on a host keeps the old plugin until it is restarted.

**Host details live in `.env`, which is not in this repo either.** The repo is
public and holds no host names, addresses or usernames. `.env` is host-specific, so
it lives in the personal config dir with the rest of it — `oc-sync` reads
`OC_HOSTS` (whitespace, comma or newline separated) and optional overrides from
there, and the repo ships `.env.example` as the template. With no `.env` anywhere,
the script falls back to `~/.oc-hosts`. `.env` is sourced before the
script's defaults, so it wins over exported variables. `OC_SYNC_ENV_FILE` overrides
the path, and both `.env` locations are tried in the order config dir, then repo,
so a checkout that keeps one beside the script works too.

**`~/bin/oc`, `~/bin/oc-notify` and `~/bin/oc-sync` dangle.** They are
symlinks into `~/.config/opencode/bin/`, and that target directory does not exist.
Repoint them at `~/Projects/lacode/bin/` (and refresh `PATH`, or nothing on this
machine finds `oc`).

Two ordering and scope rules that are easy to get wrong:

- **`src/` must land before `plugins/`.** The files in `plugins/` are one-line
  re-export shims over `src/plugins/`, and those import `../lib/`; a plugins-first sync
  leaves them unable to resolve on next restart. `presets/` must land too, or the host
  silently falls back to the pool's built-in defaults instead of the intended models.
- **No module under `src/` may export a plugin except `src/index.ts`.** opencode calls
  every export of every file in `plugins/` as a plugin and uses the return value as a
  hooks object, so a helper left there is a broken plugin, and opencode stops
  starting — `verifyWriterRule` is the case that lives in `src/lib/` for this reason.
  The published package follows the same rule with a single entry point that merges
  the three hook factories.
- **`node_modules`, `package-lock.json`, `tests/` and `dist/` are not synced.** Each
  host keeps its own install and SDK version. Consequence: the `1.18.34` pin in
  `package.json` is **not** enforced anywhere — it is documentation, not a
  constraint. Verify the SDK version on a host before assuming parity, and keep it
  equal to that host's opencode binary version.

One known gap, left as it is rather than papered over: the `opencode.jsonc` this
script ships points at `file:///…/Projects/lacode/dist/index.js`, an absolute path
that exists on this machine and on no host. The hosts therefore load the plugin
from the pushed `plugins/` shims and not from the config's own `plugin` entry, so
a host can go stale without any error. Decide deliberately whether hosts should
install `@lawaty/lacode` by name instead — that is a change to the config, not to
this script.

Remotes are plain rsync copies with no `.git`, so they carry no history. Local is the
only place edits are made; a remote-side change is untracked and will be overwritten by
the next sync.

## The context map

`context-autoupdate` maintains a map per project at `.opencode/context/`,
resolved from the session's own directory (`path.resolve(directory)`). So
`/home/yourname` gets `~/.opencode/context/`, and a different project gets its own.

It is deliberately **not** in git and **not** synced to the other hosts. The map is a
derived artifact — an index regenerated from the source by `context`, not source
itself — and it is scoped to one machine's filesystem. Syncing it would push a
description of this host's projects onto hosts that have different ones, and committing it
would churn on every session that touches a file. The rules that generate it — the
plugin, the agent and command definitions in `src/`, and the tests — are in git and ship
to the remotes; `AGENTS.md`, `commands/context-*.md` and `rules/browser.md` are in the
personal config dir, ship to the remotes, and are in no repository at all. The map
itself is rebuilt on demand by the next cartographer run.

### The cartographer's own sessions

Every cartographer run creates a session, writes its transcript to
`~/.local/share/opencode/lacode/cartographer/` (the last 20 in full) and then
deletes the session, so the run does not sit in your session list. The transcript
is written first on purpose: it is the only record of what the run did, and
the delete is what keeps the list clean.

If a run dies between creating the session and starting the turn, the session
would otherwise be left behind with nothing in it — an entry that opens as
blank. Retirement now covers that whole gap, and a delete that does not take is
retried once and then logged as `the cartographer's session could not be
removed from the session list`.

To clear sessions the retirement never reached — the runs from before it
existed, which are hundreds on a long-lived machine:

```sh
node scripts/retire-cartographer-sessions.mjs --dry-run
node scripts/retire-cartographer-sessions.mjs
```

It talks to the opencode server over its HTTP API, needs
`OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD`, and writes a compact
record of everything it removed to
`~/.local/share/opencode/lacode/cartographer-archive/`.

There is no `rules/context-protocol.md`; the global `AGENTS.md` covers it. What the
personal config dir does carry is `rules/browser.md`, whose Playwright anti-loop rules
exist nowhere else and are loaded through the `instructions`
key in the personal `opencode.jsonc`. The context map is deliberately **not** in
`instructions` — that would inject all the files into every session and every pooled
subagent, defeating the read-one-file rule `AGENTS.md` states.

Trigger: a root session goes idle after editing files outside the map. It borrows a pool
slot, spawns `context`, and applies changes. `context` is the single
writer; other agents read the map but never write it.

Two operational rules:

- **A `finished` log line is not evidence the map changed.** A run blocked from writing
  resolves identically to a successful one. The plugin now reports `changed: N`, counts
  files that actually moved on disk, and warns at `changed: 0`.
- **If the map goes stale, check the one-writer permission rule first.** opencode evaluates
  file permissions against the path **relative to the project root**, not the absolute path
  the tool was handed — a write of `/repo/.opencode/context/architecture.md` is evaluated as
  `.opencode/context/architecture.md`. Patterns are anchored, so neither spelling covers
  every project on its own: `.opencode/context/**` fires for a normally-rooted project but
  not when the project root is `/`, and `*/.opencode/context/**` fires *only* when it is.
  **Both are required.** A rule in only one form silently covers nothing when the project
  root is the other shape: the relative form matches nothing from `/`, and the absolute
  form matches nothing from a repo root. `src/lib/writer-rule.ts` checks the form that
  applies to the running project's root and logs an error naming the offending rule;
  `tests/permission-test.mjs` pins both directions, including against the real
  `opencode.jsonc`.

Force a run with `/context-update` rather than waiting for the idle trigger.

The map directory holds a sixth file, `active.md`: the active backlog of work in
flight, grouped by the ISO week each task was opened in. A task that is not marked
`[x]` is open and is never removed, however old it is; a task that is finished and
dated is kept for a week after it was finished and is then dropped. The window is
enforced by the plugin, not by the cartographer: `src/lib/active-backlog.ts` owns
the arithmetic, and `context-autoupdate` normalizes the file on every edit of it
and once at session start. A line that vanishes from `active.md` was aged out by
that rule, not lost — the boundary is strict, so a task finished exactly seven
days ago is still kept. A task that is finished but carries no date cannot age
out at all, and stays until it is dated or removed.

## Session retention

opencode has no session retention of its own — no age prune, no TTL, no bulk
delete — so every session a machine has ever had sits in the list with its
messages, parts, todos and event rows behind it, and the database grows until
it is unwieldy. `scripts/retire-old-sessions.mjs` is the sweep that takes them
out: every session past the window, and every row that belongs to it. It is
the general case of what `scripts/retire-cartographer-sessions.mjs` does for
the cartographer's own runs.

```bash
node scripts/retire-old-sessions.mjs --dry-run
node scripts/retire-old-sessions.mjs --days 60 --grace-hours 6
node scripts/retire-old-sessions.mjs --directory /path/to/project --limit 100
```

`--dry-run` reports what would go and changes nothing. `--days N` sets the
window by creation time (default 30). `--grace-hours N` skips anything touched
more recently than that (default 24). `--directory D` selects the sessions
rooted in that project directory and is repeatable; a child always goes with
its parent, so the run can reach a session in another directory. `--limit N`
caps how many top-level sessions go in one run (default 0, no limit); a session
brings its children with it, so the number of retired sessions can be higher.
`--vacuum` rewrites the database afterwards so the freed pages go back to the
filesystem.
`--no-events` keeps the event rows of the sessions it removes.

**A session in use is never a candidate.** The grace window is what says so: a
session touched within the last hours is left alone however old it is, so an
open tab or a long run keeps its history while the sweep takes what nobody has
come back to.

Every statement goes through opencode's own CLI (`opencode db --format json
"<sql>"`), so there is no sqlite module to install and nothing to import. The
tool stays inside ES2019 on purpose, and that is what lets the same file run
on the remote host's node 12.22.9 and on this machine's node 26.

**What is kept is a compact record, not the transcript.** Each retired session
leaves one entry under `~/.local/share/opencode/lacode/session-archive/` — the
id, the title, the directory, the project, and when it was created and last
updated. The transcript itself is not kept: the record tells you what used to
be in your list, and the messages are gone.

**The file does not shrink on its own.** `auto_vacuum` is 0 in these
databases, so the pages a deleted session frees stay in the file and the
database keeps the size it had. `--vacuum` rewrites it and gives the space
back, and it needs free disk roughly the size of the database to do it — the
rewrite writes a second copy before it replaces the first.

**The daily timer** is two systemd user units in `systemd/`:
`lacode-retire-sessions.service` and `lacode-retire-sessions.timer`. Install
them per machine:

```bash
mkdir -p ~/.local/lib/lacode ~/.config/systemd/user
cp scripts/retire-old-sessions.mjs ~/.local/lib/lacode/retire-old-sessions.mjs
cp systemd/lacode-retire-sessions.service ~/.config/systemd/user/
cp systemd/lacode-retire-sessions.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now lacode-retire-sessions.timer
```

The script lives under `~/.local/`, beside where the repo's other personal
helpers live (`~/.local/bin/`), and outside `~/.config/opencode/` — so the
opencode config tree stays exactly what the sync writes.

The units are per-user: `%h` in the service is the home directory of the user
who enabled it, so one unit file serves every user. `/usr/bin/node` is spelled
out because a systemd unit has no PATH worth trusting, and the same absolute
path works here and on the remote host for the reason above.

`OnCalendar=daily` with `RandomizedDelaySec=2h` puts the sweep somewhere in
the first two hours after midnight, off the top of the hour where every other
timer on a machine fires. `Persistent=true` means a run missed while the
machine was off happens on the next start.

**A timer only fires while the user manager is alive.** On a host where the
manager does not survive the last logout, the timer never runs and nothing
says so:

```bash
loginctl enable-linger <user>
```

That is what keeps the sweep firing on a machine nobody is logged into.

## Event log retention

The `event` table is not telemetry. It is a second copy of every session
transcript opencode has ever recorded — the prompts, the tool output, whole
file contents and diffs — in rows of up to 30 MiB. It is 68% of the local
database and 86% of the host's, it grows around 289 MB a day locally, and
opencode has no age prune, no TTL and no bulk delete for it: without a sweep of
its own it only ever grows.

`scripts/prune-old-events.mjs` is that sweep. It deletes the event rows older
than the window, for the sessions that are not protected.

**The age is read out of the row id.** The `event` table has no timestamp
column at all — its columns are `id`, `aggregate_id`, `seq`, `type` and `data`.
The id is `evt_` plus 12 hex characters plus 14 random base62 characters, and
those 12 hex characters are a big-endian 48-bit block whose top 36 bits carry
the row's epoch millis. The tool turns the cutoff into an id prefix and
compares id strings, which the primary key index answers as a range scan.

**Three protections, and each one is there for a reason.** A session that takes
part in opencode's session sync — its `event_sequence.owner_id` is set — is
never touched: its log is replayed to other machines, and a hole in it makes
the replay fail hard. A session that belongs to a workspace is never touched:
its log is warped to a remote. A session touched inside the grace window is
skipped, so a session in active use keeps its whole log.

**The `event_sequence` cursor rows are never deleted and never reset.** They
are the client's position in the stream, and resetting one would make the
client believe it is behind and replay the session from the start.

```bash
node scripts/prune-old-events.mjs --dry-run
node scripts/prune-old-events.mjs --days 14 --grace-hours 3
node scripts/prune-old-events.mjs --limit 1000 --vacuum
```

`--dry-run` reports what would go and changes nothing. `--days N` sets the
window by the age of the row (default 7). `--grace-hours N` skips anything
touched more recently than that (default 1). `--limit N` caps how many rows go
in one run (default 0, no limit). `--vacuum` rewrites the database afterwards
so the freed pages go back to the filesystem.

**The daily timer does not vacuum.** `auto_vacuum` is 0 in these databases, so
the pages a deleted row frees stay in the file and are reused: the database
stops growing at the size it had reached, and a vacuum is what actually hands
the space back to the filesystem.

Every run appends one JSON line to
`~/.local/share/opencode/lacode/event-prune.jsonl`.

**The daily timer** is two systemd user units in `systemd/`:
`lacode-prune-events.service` and `lacode-prune-events.timer`. Install them per
machine:

```bash
mkdir -p ~/.local/lib/lacode ~/.config/systemd/user
cp scripts/prune-old-events.mjs ~/.local/lib/lacode/prune-old-events.mjs
cp systemd/lacode-prune-events.service ~/.config/systemd/user/
cp systemd/lacode-prune-events.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now lacode-prune-events.timer
```

The timer fires at 03:00 with an hour of random delay on top of it. The slot
is deliberate: the session-retention sweep runs in the 00:00-02:00 window, and
both tools write to the same SQLite database through the `opencode db` CLI —
two concurrent writers would collide on the database lock.

**The transcript itself is not touched.** It lives in the `message` and `part`
tables, and the TUI reads it from there, so pruning the event log does not
lose the conversation; the history rendering does not read the event table at
all. A client that rebuilds a session from the event stream alone will see a
shortened log, and so will a replay of a session that none of the protections
above covers.

The id encoding only tells times apart within 795 days of each other, because
the millis it carries are truncated to 36 bits. That does not matter here:
the session-retention sweep takes a session out well inside that window, so
its event rows are gone long before their age could be misread.

## Version control

This repo (`~/Projects/lacode`) is a git repository, public at
`github.com/lawaty/lacode`, tracking `origin/master`. It is the package only. The
personal opencode config at `~/.config/opencode` is **not a git repository** — it
has no `.git`, no history and no review.

Not covered by git:

- **The whole personal config dir** — `opencode.jsonc`, `AGENTS.md`, `commands/`,
  `rules/`, `.env`, the prompt files. It is one person's configuration and is not
  published, but note that `AGENTS.md` and `commands/context-*.md` are
  the rules every context map is generated from, and they are versioned nowhere.
- **The context map** (`<project>/.opencode/context/`) — intentionally outside git and
  not synced. Derived, per-project, and rebuilt on demand; see
  [The context map](#the-context-map).
- `~/bin/oc-hosts` — host-specific, deliberately outside version control.
  `bin/oc-sync` reads the host list from `.env`; `~/.oc-hosts` remains only as a
  fallback for when no `.env` is present.
- The remote hosts — rsync copies, no history.

Before publishing anything here, note that the repo is **public**: treat every tracked
file as public. Keep host names, IPs, and credentials out of it, and keep `auth.json`
in `~/.local/share/opencode/` where it is.

## Troubleshooting

**A pooled spawn went to an unexpected model.** Read the `routed` log line for the `slot=`,
`weight=`, `ceiling=` and `load=` fields, then check for a `limit.<provider>__<model>.json` file — a
stale one with a future `until` will keep diverting work. If the model is right but the slot
is not the one you expected, that is the rotation: routing walks the weighted run from a shared
cursor and takes the first slot that is neither cooling nor at its ceiling (twice its weight) —
not the emptiest and not the heaviest.

**Everything routes to one provider.** Check for `limit.*.json` files cooling the other.
A provider-wide `free_tier_limit` cools every slot on that provider at once, which is
intentional: the alternative is a hang.

**`oc-sync` says `opencode.jsonc not found`.** `CONFIG_DIR` is pointing at the wrong
  tree. It is `~/.config/opencode` by default and nothing else — if it says the repo, an
  `OC_SYNC_CONFIG_DIR` is set pointing at the wrong tree; unset it or point
  it at the config dir. `--scripts-only` skips the check and the config entirely.

**The map is stale / the cartographer reports success but nothing changed.** Look for
`context map is not writable` in the log first, then confirm the map files' mtimes.

**Suspected hang.** Run `pool_status`. If a claim is older than 5m with 3m of silence it
is aborted automatically within ~30s; if the watchdog line shows no recent sweep, restart
the process — the timer is not running.

**A plugin change appears to have no effect.** It is almost certainly not reloaded. Check
process start time against file mtime — and on this machine check that `dist/` is newer
than `src/`, because that is the copy the config loads.
